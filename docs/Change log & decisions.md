## 2026-10-23 — requirements.txt made complete (runtime deps only)

*   Was `flet>=1.0.4` + `PyYAML>=6.0.3`; now `flet[cli,desktop]>=1.0.4` + `PyYAML>=6.0.3`, each with a comment saying what it is for.
*   Reason: in Flet 1.x the desktop runtime is an **extra**, not a dependency. ## 2026-10-23 — Chain: formula moved behind a "View formula" button

*   Chain cards now show only the hop ("Centimeter (cm) → Meter (m)") and that hop's values ("2500 → 25"). The inline formula text, the "MD formula applied backwards" note and the chain copy button were all removed.
*   Each card carries a "View formula" button that reveals that hop's formula and collapses it on a second click. For a hop that reused an `MD` formula backwards the formula is shown already flipped, so what is on screen is always the formula that was actually applied: configured `x + 273.15` is shown as `x - 273.15`.
*   Reason (user request): the cards were busy — the formula was always visible even when it was not wanted, and announcing "applied backwards" is redundant once the formula itself is presented in the direction it was used.
*   Implementation: `_flip_conversion_formula()` builds the reversed formula as an AST and unparses it, mirroring the algebra of `_invert_conversion_formula()` (+ ↔ −, × ↔ ÷). Dividing by a fraction is rewritten as multiplying by its reciprocal, so `(x * 9/5) + 32` flips to `(x - 32) * 5 / 9` and `(x - 32) * 5/9` flips to `x * 9 / 5 + 32`. `ConversionStep` gained `applied_formula` (the configured text is still kept in `formula`); `describe_conversion_step()` was deleted.
*   Verified two ways: a property check over all 76 `MD` formulas in `conversions.yaml` (every flip round-trips numerically through the app's own evaluator and agrees with the numeric solver), and a headless Flet session driving the real UI — formulas hidden until clicked, one button per hop, reveal/hide toggle, flipped formula on a reversed hop, a mixed 3-hop chain (Rankine → Kelvin), zero-step chain with no buttons, chain cleared on unit change, error path intact. Scripts: `/tmp/flip_test.py`, `/tmp/chain_probe4.py`.
*   Probe gotcha: a card's title and its value line both contain "→", so matching "→" alone conflates "1. Centimeter (cm) → Meter (m)" with "2500 → 25".
*   Batched shell calls race: launching a probe and reading its output file in the same parallel batch reads the file before the probe writes it. Chain dependent commands with `;` in one command string instead.

## 2026-10-24 — `%` on the regular pad, `±` on both pads

**Requested:** a `%` button on the regular calculator, and a `±` button on both calculators (`±` confirmed as the right glyph — it is the standard sign-change key; iOS writes the same key as "+/-").

**What the app does now**

*   Regular keypad: `AC ⌫ ( ) ± %` on the utility row, then the unchanged digit/operator rows. Putting the two new keys in the existing top row instead of adding a row keeps the pad exactly as tall as before, which matters because the pad already fills the window in scientific mode.
*   Scientific keypad: no duplicate keys. The scientific block is now `sin cos tan √` / `log ln π e ^` / `Set Variable, Insert Variable` above the regular rows — `(`, `)`, `%` and `±` come from the shared utility row, so nothing is printed twice and every `key-<label>` stays unique (previously `(` and `)` were duplicated in scientific mode).
*   `%` inserts Python's modulo, the same as the scientific key always did: `9%2` → 1, `7%2.5` → 2. `Decimal`'s remainder truncates the quotient, so the result keeps the dividend's sign (`-7%2` → -1, `7%-2` → 1) rather than Python's floor remainder (`-7 % 2 == 1`); `5%0` reports "Invalid result". **Not** percent-of (`x/100`) — flagging that as the open product question.
*   `±` is new logic in `toggle_sign()` (module-level, so it is unit-testable without an app): it edits rather than appends. It flips the sign of the last number typed, or of the result right after `=`; `5*3` → `5*-3`; a second press removes the sign instead of stacking one (`5--3` → `5-3`); if the expression ends on an operator the sign goes at the end for the number about to be typed (`5-` → `5--`, so typing 3 gives 5 − (−3)); a numberless expression is untouched. Pressing `±` never leaves result mode, so `-5` straight after `=` is still a result.
*   Keypad key handling: `±` is handled before the "any other key starts a new entry" block in `press()`, and the `⌫`/`AC`/error paths are unchanged.

**Docs:** `calculator_spec.md` gained a "Calculator keypad" section (keys per pad, one-key-once rule, no height growth, `%` semantics incl. the dividend sign, all `±` rules) plus a Testing bullet about the expression-engine file; `README.md` lists the new test file. No data/YAML changes.

## 2026-10-24 — `%` on the Regular Calculator is now a desk-calculator percent key; Length factors made exact

**Requested:** the regular calculator's `%` should behave like the percent key on a physical desk calculator (the earlier entry above flagged "percent-of vs modulo" as the open product question — this settles it), and the Length group's rounded conversion factors should be replaced by their exact legal anchors.

**Decision:** `%` means two different things, one per pad. The Regular Calculator gets desk-calculator percent; the Scientific Calculator keeps the modulo operator, because there `%` is used as a programming operator and percent would be useless.

**What the app does now (Regular pad)**

*   `50%` → 0.5; `200+10%` → 220 and `200-10%` → 180 (the share of the number on its left); `200*10%` → 20 and `200/10%` → 2000 (plain fraction); chaining re-applies the rule to the running total, so `200+10%+5%` → 231. Pressing `%` with nothing in front of it does nothing, and a lone `%` shows an error instead of a traceback.
*   Implementation: a postfix `%` is not Python syntax, so `apply_percent_operators()` rewrites it into a marker call before parsing — `200+10%` becomes `200+_percent(10)` — walking back over the digits, or over a parenthesised call such as `sqrt(4)%`. `evaluate()` divides a bare marker call by 100, and `percent_share()` turns `+ _percent(n)` / `- _percent(n)` into that share of the already-evaluated left operand. Only the regular pad is rewritten (`calculate()` applies it when `scientific` is False), so the scientific pad's modulo is untouched.
*   `±` had to learn the same distinction, otherwise it would treat the regular pad's `%` as an unfinished operator: `toggle_sign()` takes a `percent_is_modulo` flag, so `200+10%` negates its last number while `9%` on the scientific pad is mid-entry and gets the sign at the end.
*   Unparsable input now reports `ERROR_INVALID_EXPRESSION` ("Invalid expression") instead of the bare "Error".

**Unit conversion data (**`**src/assets/conversions.yaml**`**, Length group)**

*   Rounded literals replaced by the legal anchors: `inch → millimetre` is `x * 25.4` (was `meter → inch = x * 39.37007874`), `mile → metre` is `x * 1609.344` (was `x / 1.150779448` for mile → nautical mile), `nautical_mile → metre` is `x * 1852`, `light_year → metre` is the exact integer `x * 9460730472580800`, AU stays 149597870.7 km. So inch → millimetre is now exactly 25.4 instead of 25.4000000001…, and nautical mile → metre exactly 1852 instead of 1851.9999994….
*   Integer literals are exact however long, because the engine parses an `int` constant through `Decimal(str(int))`; only decimal literals are capped at the 15 significant digits that survive float parsing. That is why the light-year is written as a 16-digit integer and the parsec keeps 13 digits (`x / 3.2615637771674`).
*   The parsec is the one Length hop that cannot be exact at all: it is 648000/π astronomical units, hence not a rational number. It is excluded from the exactness sweep by name, with the reason in the YAML comment and in the test.

**Tests**

*   `tests/test_calculator_engine.py`: 56 → **96** tests, `%` split into a percent block (regular) and a modulo block (scientific), plus direct coverage of `apply_percent_operators` and `is_percent_call`.
*   `tests/test_conversion_engine.py`: 75 → **82** tests; `LENGTH_DRIFT` and its `xfail(strict=True)` marker deleted, exactness sweep extended over the whole Length group (parsec excepted).
*   `tests/test_app.py`: 6 → **7** UI tests; the keypad test asserts `200+10%` previews `220` on the regular pad and the scientific assertions keep `9%2` at `1`.
*   Verified: `.venv/bin/python -m pytest -k engine` → **178 passed** in ~3 s.

**Docs:** `calculator_spec.md` — the Length "known deviation" paragraph is replaced by the exact-anchor rule plus the parsec exception, the "Calculator keypad" section splits `%` per pad and extends the `±` mid-entry rule, and the Testing section records the removed marker. `README.md` — exact anchors + parsec caveat, `-k engine` now selects both engine files, percent/modulo described in the test bullet. Trilium: the "Testing — pytest + flet test suite" note is rewritten to match; this entry is appended here because the note editor only offers whole-note rewrite or append for rich-text notes (the newest-at-top convention is broken by this placement, not by the content).

## 2026-10-24 — single-file app split into 11 modules; `src` re-registered inside packaged builds

**The split (spec §"Source layout", done for real this time)**

*   `src/main.py` was **1607 lines** holding everything; it is now **52 lines** (entry only: `main(page)`, `run_app()`, the `__main__` guard). New modules, matching the module names the spec already listed: `config.py` (constants + `Decimal` precision + `CONVERSION_CONFIG_PATH`), `calculate.py` (expression engine, 426 lines), `conversions.py` (conversion config + route finding, 350), `ui.py` (`CalculatorApp` state/display/preview/mode wiring, 668), `keypad.py` (both pads' rows + `make_key`), `conversion_view.py` (`ConversionView`), `history_view.py`, `variable_dialogs.py`, `clipboard.py` (`ClipboardService`), `styles.py`, `__init__.py`.

**Packaging gotcha found on the way (this is the part worth remembering)**

*   `flet test` / `flet build` copy the **app folder itself** (`[tool.flet.app] path = "src"`) **flat** into `build/flet/tests/app/` and put _that folder_, not the project root, on `sys.path` (`_prepare_temp_dir`, `_copy_project_files_into` / `_copy_python_app_files_into` in `flet_cli/commands/build_base.py`, plus `_build_pth()`). ## 2026-10-26 — "Emulator is not responding" was the host, not the app

The Android emulator window repeatedly triggered an "is not responding" dialog while AnythingCalculator itself ran perfectly (verified: 21 scripted taps all landed, display showed `444444444444444444444`, screenshot had no dialog).

*   **The dialog is not Android's and not the emulator's.** The string "not responding" appears nowhere in the emulator binaries except an unrelated Qt WebEngine library, and the guest reported **0** `ANR in` entries even under a 50-tap burst, never lost `mCurrentFocus`. It is the GNOME Shell X11 liveness watchdog: `org.gnome.mutter check-alive-timeout`, default **5000 ms**. The emulator's Qt window is an X11 client under XWayland, so any stall over 5 s gets the window declared dead.
*   **What caused the stalls.** Host saturation: `clamscan` was pinned at 99 % of a core, VS Code's renderer spiked to 100 %, 4 vCPU guest on a 4-core host, and ~6 GB swapped with heavy I/O. The emulator also runs **niced at +5** while `gnome-shell` runs at **−5**, so under contention the emulator is the first thing starved (negative nice is denied to this user, so it cannot be counteracted from the shell).
*   **KVM was never the problem.** My "0 kvm threads" reading was a bad `grep`. Proof of hardware acceleration: the process fds `/dev/kvm`, `kvm-vm` and `kvm-vcpu:0/1/2`, and its log line `CPU Acceleration status: KVM (version 12) is installed and usable` plus QEMU's `-enable-kvm -smp cores=4 -m 4096`.
*   **Changes made:** AVD `hw.cpu.ncore` 4 → **3** (leave a core for the host), `hw.ramSize` 4096 → **3072** MB, emulator launched without `-verbose` (that flag logged a DEBUG line per rendered frame: 1131 debug lines vs 8 warnings), and `check-alive-timeout` 5000 → **20000** ms so brief host stalls stop being reported. The RAM/core change invalidates the `default_boot` snapshot, so the next boot is cold (31 s).
*   **Measured afterwards on a quiet host:** 50 taps at 45 ms round-trip, 0 ANRs, boot 31 s (vs 40 s with the scan running), emulator log 11 KB instead of 139 KB.
*   The emulator's own exit path is a stall too: it saved the `default_boot` snapshot in 3902 ms on quit, which alone nearly trips a 5 s watchdog.

*   **Mechanism confirmed, not guessed - the frozen thing is the _event loop_, not the pixels.** The check is EWMH `_NET_WM_PING`: `gsettings describe org.gnome.mutter check-alive-timeout` reads "Number of milliseconds a client has to respond to a ping request in order to not be detected as frozen"; `libmutter-18.so.0` carries the `_NET_WM_PING` / `WM_PROTOCOLS` / `check-alive-timeout` strings; the XWayland root window on `:0` advertises `_NET_WM_PING` in `_NET_SUPPORTED`; and each of the emulator's own top-level windows (`0x3000007` device screen "Android Emulator - anycalc:5554", `0x300001a` "Extended Controls", `0x300000a` toolbar) lists `_NET_WM_PING` in its `WM_PROTOCOLS`. *   The emulator process owns **four** pingable top-level windows, so the dialog may have been about the toolbar or Extended Controls window rather than the device screen.
*   `-no-window` ("disable graphical window display") removes the X11 client entirely - the only setting under which the desktop can never complain; screenshots still work via `adb exec-out screencap -p`.

## 2026-10-31 — pi page: a bar weighted by work, a progress card on a clock, and a paged digits dialog

**Symptoms reported:** "the progress bar isnt moving", then "the progress only updates when a button is pressed — make it update every 0.5s automatically", and "what is going on with these scrollboxes in the view digits".

**The bar, cause 1 — it was weighted by terms.** `fraction` divided terms done by terms total, so it stood near two thirds through the whole tail (the products that combine the terms, the last square root, the division) and then snapped to 100 %: it looked finished, or stuck, long before the run was. It now divides measured **work** (`work_done / work_total`) — the binary split knows what it costs before the first term (`pi.run_weight`), so a run has an honest percentage from the start.

**The bar, cause 2 — its track was the card's own colour.** `bgcolor=CARD_BACKGROUND` made the unfilled part invisible, so a filling bar read as a growing blob. Now `bgcolor=PANEL_BACKGROUND`, `bar_height=10` — exactly what the spec already demanded.

**The bar, cause 3 — nothing was pushing it on the clock.** The worker's report callback was the only painter, and one huge multiplication produces no report at all, so the card sat still for precisely the longest stretch of a run. Now:

*   `start_run` schedules `_paint_loop` with `page.run_task` — **the page's own event loop, not a second `page.run_thread`**. `run_thread` queues on an executor shared with every other handler in the app, so a painter can sit waiting for a worker slot; a painter that never got one is a bar that seems to move only when something else repaints the page. `self._paint_task` keeps the reference, because an unreferenced task can be collected mid-run.
*   The half second is anchored to a schedule (`loop.time() + PROGRESS_PAINT_SECONDS` each pass) rather than a chain of `time.sleep`s: a loop sharing the interpreter with a computation over huge integers wakes late by tens of milliseconds at a time, and chained sleeps add that lateness up until the card drifts to a paint every two thirds of a second.
*   The rate cap lives **inside** `_paint_progress`, not in either caller, so the clock and the engine's checkpoints spend **one** shared budget of two frames a second. The worker still paints with each report — a checkpoint is often the only progress that can be shown while the interpreter is busy with one multiplication — but a million reports cannot become a million page updates.
*   `_last_paint` is reset in `__init__` and `start_run` (a stale stamp from a previous run would otherwise swallow the first frames of the next), and `_card_final` stands the painter down the moment a run ends, so a late tick can never write a mid-run number over what a finished or cancelled run reports.
*   The clock **survives a frame that fails to reach the client**: the tick is wrapped, the task keeps asking on schedule and the status line says `progress display failed: …`. An unwrapped `await`-task dies on one exception and says nothing — which is precisely the reported symptom, a bar that only moves when a button handler happens to repaint the page.

**The digits view, cause — the list grew under the reader's fingers.** The dialog used one endless list extended on every scroll event (`_fill_more_on_scroll`, a batch at a time). A scrollbar can only be honest about a length that does not move: that list kept re-measuring a distance that changed mid-drag, so the thumb resized while it was being dragged, the end kept running away from it, and the thumb ended up a meaningless sliver. There is no scroll handler left: the dialog holds **one page** of `DIALOG_PAGE_DECIMALS = 10_000` decimals, which is **replaced** rather than appended when the reader turns a page, with First / Previous / Next / Last buttons (disabled when there is nowhere to go), a footline saying where they are ("decimals 10 001 to 20 000 of 60 000 — page 2 of 6"), a page turn that returns the scroll to the top of the new page, and `DIALOG_SCROLLBAR_GUTTER = 14` so the thumb no longer draws on top of the digits it is about. A hundred million decimals are still never on screen at once.

**Measured in the running app, with nothing pressed** (a temporary probe driving the real `AnycalcApp`, screenshots through `page.take_screenshot()`):
*   20 000 000 digits: the card read 4.7 % → 8.6 % → 13.1 % → 19.4 % → 24.2 % → 30.5 % → 38.7 % → 43.9 % at 2 s intervals, and **every screenshot differed from the one before it** (33–114 changed sample pixels across the frame).
*   Counting repaints directly: 60 repaints in 46.7 s on that run, ~2 a second between samples; a 1 000 000-digit run took 4 repaints in 1.9 s = **2.16 a second**, i.e. the full rate the cap allows.
*   Cadence, measured as the gap between repaints on a 20 000 000-digit run (43 repaints, nothing pressed): **0.502, 0.500, 0.508, 0.542, 0.503, 0.507, 0.509 …** — the card moves on the half second. The exceptions are the ones physics allows: 0.92 s, 1.22 s and, inside the final square root and division, up to 4.5 s, because a single C-level multiplication of numbers that size holds the interpreter and no Python code at all can run in between. Screenshots at 4 s, 8 s, 12 s, 16 s and 20 s of that run (25.4 % with 652 284 / 1 410 275 terms and "about 24 s left", then 100 % and "took 34 s") differ from each other in every byte.

**Tests** (`tests/test_pi_view.py`, 59 pass): the painter is a task and not a thread; a run's card paints about twice a second with no report and no press; a tick and a report never cost two frames in one half second; a thousand reports cost at most two frames; a finished run keeps its own words against a late tick; plus the paging rules (page math, replaced-not-appended lines, both ends unreachable by pressing, short last page never padded, one-page numbers have nowhere to turn). `test_a_thousand_reports_cost_at_most_two_frames` and the tick/report test are new for this change.
