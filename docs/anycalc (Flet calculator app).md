Working rules for this project live in the repo's `AGENTS.md`; the machine-readable feature spec lives in `calculator_spec.md`. This note is the human-facing documentation hub — design decisions, architecture, and change log go here rather than in loose text files.

## Architecture of `src/main.py`

Top-level, non-UI code:

*   `load_conversion_config()` — reads/parses `conversions.yaml`, returns `(unit_groups, conversions)`; raises clear errors on invalid YAML. Conversions have no `id`, only a `name`; `formulas` is a dict keyed by number, so iterate `.values()`
*   `find_conversion_path()` — graph search for a route between two units; two passes (`allow_reverse` False then True) so fully-forward routes win. Returns the list of `(formula, reversed)` hops it chose
*   `_contains_conversion_input()` / `_evaluate_conversion_formula()` — forward evaluation of a formula AST
*   `_invert_conversion_formula()` — algebraically reverses `MD` formulas by walking the AST and returns the _value_; `UD` formulas are never reversed
*   `_flip_conversion_formula()` — same algebra, but builds the reversed **formula** as an AST and unparses it for display (`x / 100` → `x * 100`, `(x * 9/5) + 32` → `(x - 32) * 5 / 9`). Dividing by a fraction is rewritten as multiplying by its reciprocal so the output stays readable
*   `ConversionStep` / `ConversionOutcome` — frozen dataclasses describing one applied hop (from/to unit ids, configured `formula`, `applied_formula` as actually used, formula type, `used_backwards`, value in, value out) and a whole conversion
*   `convert_units()` — end-to-end conversion entry point; returns a `ConversionOutcome`, so the UI can show the chain of operations rather than only the answer
*   `format_conversion_value()` — plain-text rendering of a converted value
*   `calculate()` — the expression evaluator: parses with `ast`, evaluates node-by-node, `Decimal` arithmetic, trig helpers honoring deg/rad, named variables
*   `copy_to_clipboard()` / `make_copy_button(get_value)` — shared clipboard helper and the small icon button factory; the getter is read at click time so a button can never copy a stale value

UI code lives inside `main(page: ft.Page)` — drawer navigation, keypad rebuild, variable prompts, history rendering, and the inline conversion form.

*   **Conversions are live.** There is no Convert button: `run_conversion()` runs on the value field's `on_change` and on both dropdowns' `on_select`. A non-numeric or empty value clears the result and the chain silently; only real failures set `result_field.error`. The chain cards sit under the result: one card per hop showing the unit transition and that hop's in → out values, with the formula hidden behind a per-card "View formula" toggle (a reversed hop shows its formula already flipped). The chain itself is not copyable.
*   **The calculators have a live answer.** `preview_answer()` evaluates the current expression and `refresh_preview()` shows it as a small grey number under the display box (`preview_value` inside `preview_slot`), hiding it when the expression is empty, half-typed, already a number, an error, or a result already in the display. It is refreshed from every path that can change the expression or its meaning: `update_display()`, `handle_display_change()`, `toggle_angle()`, `assign_variable()`, `set_mode()`. `promote_preview()` runs on `=`: the grey number grows to the display size, turns white, slides up and fades over `PREVIEW_MORPH_MS`, then `page.run_task(finish_preview_morph, token)` resets the slot (the token ignores a stale timer, `preview_morphing` stops `refresh_preview()` from cancelling the animation).

## Packaging & build (`pyproject.toml`)

*   **The entry point is inside** `**src/**`**, declared twice on purpose:** `[tool.flet.app] path = "src"` + `module = "main"` (used by `flet run` / `flet build`) and `[project.scripts] anycalc = "src.main:run_app"` (installed by `pip install -e .`). Setuptools side: `packages = ["src"]`, `include-package-data = true`, `package-data = {src = ["assets/*.yaml"]}` so the YAML travels with an installed distribution.
*   `flet build linux` is run **from the workspace root**, not from `src/` — `[tool.flet.app]` is what lets the CLI find `src/main.py` there. `validate_entry_point()` (`flet_cli/commands/build_base.py:992`) fails with "main.py not found in the root of Flet app directory" if `app.path` / `app.module` are wrong; `--module-name` is the CLI override.
*   The `[tool.flet]` keys that matter here: `org`, `product` (app id `com.github.greentruck50.anycalc`, product label), `app.path`, `app.module`, `linux.categories`. Others available: `artifact`, `company`, `copyright`, `bundle_id`, `splash`, `boot_screen`, `template.*`, plus per-platform `tool.flet.linux.*` / `.android.*` / `.ios.*` / `.macos.*` / `.web.*`.
*   Verified 2026-10-23: `flet build linux --no-rich-output --yes` from the root took ~2.5 min. Artifact `build/linux/` (132 MB): native GTK runner `anycalc` embedding CPython 1:1 via `libpython3.14.so`, `app/` (`main.pyc`, `__init__.pyc`, `assets/conversions.yaml` byte-identical to the source), `site-packages/` installed **from pyproject** (flet 1.0.5 + flet-cli + flet-desktop + PyYAML), `data/flutter_assets`, `share/applications/com.github.greentruck50.anycalc.desktop`. `build/flutter` (439 MB) is the intermediate Flutter project.
*   The app is **compiled to** `**.pyc**` **by default** in the bundle — pass `--no-compile-app` to keep readable sources.
*   A bundle executes the configured module **as** `**__main__**` (`_sp_run_module_as_main()` in the generated `build/flutter/lib/python.dart`), so `if __name__ == "__main__": run_app()` fires there too; the same pattern works for `flet run` (which spawns `python -u src/main.py`) and for the installed console script.
*   Artifact smoke test: `WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/1000 ./build/linux/anycalc` ran until `timeout` killed it (exit 124) with only a benign cursor-theme warning — no Python traceback.
*   Build prerequisites on this machine: Flutter **3.44.8** (the version Flet 1.0.4 pins, from `flet/version.py`) already present at the managed path `~/flutter/3.44.8`; `find_flutter_batch()` prefers `~/flutter/<version>` before falling back to `PATH`, so a manual Flutter install is only found if it is on `PATH`. cmake, ninja, pkg-config, gcc/g++ are installed; `~/.flet/cache/` holds the build template and python-build-standalone.
*   `.venv` has **no setuptools**, so building this project (`pip wheel .`, `pip install -e .`) needs pip's build isolation — `--no-build-isolation` fails.

## Ordering: nothing is sorted, it is all file order

Verified by reading the live drawer control tree. There is no `sorted()` call anywhere in `src/main.py`.

| Surface | Current order | Where that order comes from |
| --- | --- | --- |
| Drawer: Unit Conversions items | Length, Time, Temperature, Data | Order of the `conversions:` list in the YAML; the drawer loops `for conversion in conversion_options`, and `conversion_options` is that list verbatim |
| Drawer: Calculators | Regular, Scientific | Hard-coded `NavigationDrawerDestination` literals in the drawer's control list |
| From / To dropdowns | e.g. Length: nm, μm, mm, cm, m, km, in, ft, yd, mi, nmi, AU, ly, pc, kpc, Mpc, Gpc, Tm | Order of the group's `units:` list — deliberately SI small→large, then imperial, then astronomical; **not** alphabetical |
| Chain cards | Order the hops were applied | `outcome.steps` |
| Which formula wins a route | YAML `formulas:` dict order | BFS iterates `conversion["formulas"].values()` in file order |
| History drawer | Newest first | `reversed(history[-MAX_HISTORY_ITEMS:])` |
| Variable picker | `x y z μ g m a v t d F E P p ρ r A V T q I U R f λ`, then unused letters `b c e h i j k l n o s u w` | Hand-written `_NAMED_VARIABLE_OPTIONS` + generated leftovers appended |

Two constraints to respect when reordering:

1.  **A conversion's menu label must be** `**<unit group name> + " Conversion"**`**.** `open_conversion()` resolves the group with `conversion["name"].removesuffix(" Conversion")` against `conversion_groups_by_name`; mismatching names raise "No unit group is defined for …". Reordering is safe, renaming one side is not.
2.  **The drawer is index-based.** `handle_drawer_change()`: `index < 2 → set_mode(index)`, else `open_conversion(conversion_options[index - 2])`. The `2` is the count of calculator destinations — if calculators are added, removed or grouped, that offset must change too (a flat `[(destination, action)]` list would remove the hazard).

Note: the From/To dropdowns have **no** `enable_search` (only the variable picker does), which matters on Data (43 units) and Length (18).

## Gotchas learned the hard way

*   Flet 1.0.4 `Dropdown` has **no** `**on_change**` — the selection event is `on_select` (`on_text_change` is for the filter text). Handler names passed to a constructor are looked up when the control is built, so a nested handler must be defined _above_ the control that uses it. A handler may, however, _read_ a name assigned after the `def` (it is looked up when the handler runs) — that is how the chain cards let the toggle button relabel itself, and how the live `run_conversion()` reads controls defined below it.
*   Flet 1.0 animation primitives: `ft.AnimationStyle(duration=…, curve=ft.AnimationCurve.EASE_OUT_CUBIC)` — the field is `duration` (an int is milliseconds), and `Text`/`Container` expose `animate_size`, `animate_offset`, `animate_opacity`, `animate_scale` plus `on_animation_end`. There is no `ft.AnimationEasing` and no colour animation, so a colour change during a morph snaps.
*   Flet desktop client binaries are cached in `~/.flet/client/` (one dir per Flet version) and are prepared on first use of a new version — expect a pause after a version bump.
*   Services (`ft.Clipboard`) self-register with the current page in `Service.__post_init__`; they are visible in the page's internal registry `page._services._services`, **not** in the `page.services` property list.
*   `Clipboard.get()` returns a plain `str | None`, not an object with `.data`.
*   A Flet app launched from a script prints its stdout through the CLI relay, which buffers; probes that need reliable output should write to a file, and must not rely on `page.run_task(lambda: ...)` — it requires a coroutine function (`page.run_task(async_fn, *args)` works and is what the morph reset uses).
*   `src/main.py` no longer ends in a bare `ft.run(main)`, so importing it (or `src.main`) is safe for tests; the module-level guard only calls `run_app()` when executed as `__main__`. Probes that exec the source still have to inject `__file__`, because the conversion YAML path is derived from it.
*   Probe text matching: a chain card's title and its value line both contain "→"; distinguish `1. Unit → Unit` from `2500 → 25` before filtering.
*   Parallel tool batches run concurrently — never pair a UI probe with reading its output file in the same batch.
*   `flet build` needs a few seconds to unpack the build template and the standalone Python before any error appears, and the build dir `build/` accumulates ~600 MB; a long-running `flet build` started from a tool batch must be backgrounded with its output redirected to a file.

### Graph shape (keep it this way)

Each group is a tree plus two deliberate shortcuts, so exactly one shortest route exists between any pair:

*   **Volume spine:** mm³–cm³–dm³–m³–km³; `cm³ → mL` is an identity formula (`"x"`, legal because 1 mL ≡ 1 cm³); mL–cL–dL–L–hL–kL; culinary units hang off mL; `in³ → cm³ (x * 16.387064)` is the only imperial→metric bridge; ft³/yd³/mi³/acre-ft and US liquid/dry gallons hang off in³; imperial gallon → L (`x * 4.54609`).
*   **Weight spine:** µg–mg–g–kg–tonne (+quintal, carat); two bridges to metric: `lb → kg (x * 0.45359237)` and `gr → kg (x * 0.00006479891)`; avoirdupois hangs off lb, troy + apothecaries' hang off grain.

### Accuracy policy (why the formulas look the way they do)

1.  Factors are the **legal definitions**, never rounded lookups: in = 2.54 cm ⇒ in³ = 16.387064 cm³; US liq gal = 231 in³; US dry gal = 268.8025 in³; imp gal = 4.54609 L; lb = 0.45359237 kg (1959 international yard & pound agreement); gr = 1/7000 lb = 0.00006479891 kg; dwt = 24 gr, oz t = 480 gr; carat = 0.2 g. Sources: NIST SP 811 App. B, Wikipedia (Gallon, Pound (mass), Troy weight).
2.  `calculate()` turns numeric literals into `Decimal(str(float_literal))`, so a literal longer than ~15 significant digits is silently truncated. Anything longer must be **chained through integers**: mi³ is `x / 5451776000` + `x / 27` + `x / 1728` + `x * 16.387064` (exact 4168181825.440579584 m³), acre-ft is `x * 75271680` in³.
3.  A route must never perform a non-terminating division _before_ multiplying, otherwise a value that is actually exact prints as e.g. `4.9289215937499999999…`. That is why US tbsp/tsp also carry direct mL definitions (`14.78676478125`, `4.92892159375`) instead of only routing through `tbsp → tsp (x * 3)`.
4.  Values whose true decimal expansion repeats (1 lb in stone = 1/14, 1 grain in dr = 1/27.34375, imp gal in US gal) are correct at the full 50-digit `DECIMAL_PRECISION` — they are not defects.
